# OpenGrove v0.6.5

[Simplified Chinese](https://github.com/open-grove/opengrove/blob/v0.6.5/docs/releases/v0.6.5.zh-CN.md)

OpenGrove v0.6.5 makes Store App upgrades safer, adds Stripe Connect payout onboarding for eligible overseas authors, strengthens App command and media reliability, stabilizes Employee model and reasoning defaults, and makes App publishing recovery and desktop release readiness more explicit.

## Highlights

### 1. Store App programs and persistent Workspaces are separated

Store App code now installs as side-by-side program generations outside the persistent App Workspace. Installs, repairs, rollbacks, formal-version switches, and publish-and-apply operations all change one mounted program pointer while the Workspace path and user data remain stable.

Upgrade migration validates every Workspace binding before use. Obsolete program generations are removed only when they carry a valid cleanup marker; Windows file locks can defer cleanup without blocking activation, and unknown or malformed directories are retained instead of guessed at or deleted. Error exports include a structured `store-app-layout.json` inventory of current and legacy roots, active bindings, migration remnants, and inspection failures without exporting Workspace contents.

### 2. Eligible overseas authors can complete Stripe payout onboarding

Authors routed by WW to Stripe Connect can open onboarding from OpenGrove, return through the correct production or development desktop link, synchronize account status, and follow payout progress and recoverable requirements without seeing raw upstream errors.

Country, payout provider, settlement currency, creator-signing state, and payout readiness remain server-owned decisions. The client fails closed when WW returns only part of that tuple and does not call the retired Stripe consent write path.

### 3. App command and Routine outputs fail explicitly

Successful App commands that intentionally produce no output remain successful. Structured JSON output is kept separate from Host execution metadata, Routine references support deep business-output paths, and missing fields receive visible diagnostics instead of being projected as ambiguous values.

Oversized structured output and invalid JSON now fail with stable errors rather than attempting to parse a truncated stream. Spawn failures stay separate from process stderr accounting, while bounded and truncated diagnostics are labeled clearly.

### 4. Desktop media and Room synchronization recover cleanly

When an MCP App abandons a media request, the desktop proxy now propagates cancellation to the Bridge and closes the underlying stream. Repeated canceled playback can no longer exhaust desktop connections or leave local file handles open, including on Windows.

Recoverable MCP App panel failures can retry in place. Room refreshes also persist a snapshot and its event cursor atomically, preventing a reconnect from skipping or replaying events across the synchronization boundary.

### 5. Employee model and reasoning defaults stay concrete and stable

Fresh product and App Employees receive concrete Kernel/model defaults that can resolve through existing Provider bindings. Legacy blank or `native` model values migrate once, while explicit Kernel, Provider, model, and valid reasoning choices remain authoritative.

Reasoning controls distinguish loading, supported, and unsupported states. Kernel defaults stay visible while capabilities load, unavailable Providers no longer erase known Kernel facts, Pi advertises its supported reasoning levels, and save acknowledgements no longer discard per-Kernel drafts.

### 6. App publishing recovery and desktop candidate readiness are stricter

The App publishing UI now treats Release Control's returned `allowedActions` as the authority for retry and abandon choices. Failure stage, stable code, and workflow run remain diagnostic context instead of being used to reconstruct server policy in the client.

Full desktop candidates run the complete release check once before signed platform builds, authenticate read-only access to configured deployment services, replay current known-good release gates, and use aligned Playwright and runtime dependency versions. Partial-platform runs remain diagnostic only and cannot be promoted as a formal release.

### 7. Retired Host business compatibility is removed

The retired Host-owned Story Seed work-management and contract-signing surfaces, legacy same-origin web-app mounting, and their compatibility policies are removed together. Current Apps continue through supported file workbenches, MCP App Views, declared commands, and explicit WW session injection.

The bundled runtime, protocol, desktop, editor, icon, build, and test dependencies are upgraded as a reviewed set. Claude Agent keeps its model-specific default tool surface, and generated MCP App examples follow the current capability schema.

## Compatibility and Migration Notes

- `clientReleaseNumber` for this release is `10030`.
- Upgrading from OpenGrove 0.6.4 requires no manual local-data migration. Store App program generations and Workspace bindings migrate automatically; unknown files and unverified cleanup targets are retained.
- Overseas Stripe payout support requires the matching WW settlement response and data migration to be deployed first. WW must return the complete `country_code`, `payout_provider`, and `cash_currency` tuple and expose the server-owned creator-signing result through Stripe Connect status.
- Apps that still depend on legacy `ui.kind=web-app` / `ui.kind=web`, retired Story Seed Host dashboards, or Host-owned contract-signing prompts must move to supported App surfaces and declared commands before upgrading.
- npm package publication and npm-global update paths remain disabled. Source builds and desktop releases continue to use npm normally.
- Windows installers remain unsigned until an Authenticode certificate is available, so Microsoft Defender SmartScreen may still warn on first download or launch.
