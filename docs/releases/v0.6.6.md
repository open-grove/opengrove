# OpenGrove v0.6.6

[Simplified Chinese](https://github.com/open-grove/opengrove/blob/v0.6.6/docs/releases/v0.6.6.zh-CN.md)

OpenGrove v0.6.6 separates replaceable Store App programs from user-owned Workspaces and establishes the public repository's reviewed contribution and first-release path.

## Highlights

### 1. Store App program migration is copy-validated and recoverable

Replaceable Store App programs migrate independently from persistent user Workspaces. The migration validates copied program generations before activation, keeps legacy data available for recovery, rolls back incomplete changes, and never blocks OpenGrove startup. Diagnostic exports record the layout and migration state without including Workspace contents.

### 2. Public pull requests and desktop finalization use explicit trust boundaries

Public pull requests require review by a repository administrator represented in CODEOWNERS. Desktop finalization now uses the protected `desktop-release` environment, while one release operator may still approve and complete the workflow without a second operator.

### 3. The first public release preserves the normal N-1 updater gate

Because the new public repository has no earlier GitHub Release, the `v0.6.6` candidate can use one checksum-pinned bootstrap to verify updates from the existing `v0.6.5` production installers. The path is rejected for every other version and after the first public GitHub Release exists; later releases use the normal previous-GitHub-Release path.

### 4. Kernel Runs preserve native lifecycle and tool semantics

Codex, Claude Agent, Pi, ACP, Hermes, and OpenClaw keep their native tools, cancellation, interaction, and terminal-result semantics. OpenGrove no longer applies a fixed wall-clock deadline to an entire Turn. Kernel-declared interaction deadlines are honored; Host shutdown and producer loss remain explicit liveness boundaries and are recorded without pretending that the user rejected or canceled an action.

Run state now has one authority: `RunRecord.lifecycle.taskState`, using the A2A task-state vocabulary. An `error` event records diagnostics but does not guess the terminal result; only `turn.finished.outcome` completes, cancels, rejects, or fails a Run. This prevents a recoverable Provider error from poisoning a same-Run retry and keeps user cancellation distinct from failure.

## Compatibility and Migration Notes

- `clientReleaseNumber` for this release is `10031`.
- No manual Workspace migration is required. The Store App layout migration is startup-safe and retains legacy sources until validated cleanup is allowed.
- The first-public-release workflow option is release infrastructure only; it does not change installed-client behavior or product authentication.
- Local Runs written by earlier builds with only `status` are migrated to `lifecycle` when read. New snapshots and APIs no longer publish the legacy `RunRecord.status` mirror. App or external clients that read `run.status` must read `run.lifecycle.taskState`; `/runs?status=` callers must use `/runs?taskState=`. OpenGrove Desktop upgrades its UI and Bridge together, so this is an old-data migration rather than a long-term mixed-client compatibility promise.
- Approval rejection no longer implies that the Kernel Run failed when the native Kernel can continue. Conversely, a `turn.finished` event without an explicit outcome fails closed as `terminal_outcome_missing`.
- Pending-interaction APIs can now return `canceled` for both approval and question status. Clients must handle it separately from `rejected` / `declined`; `response.system` and `response.reasonCode` distinguish Host reconciliation from an explicit user cancellation.
- Explicitly canceling an approval or question cancels the entire owning native Kernel Run, not only its card. Other Runs on the same Kernel are unaffected.
- This release does not promise to resume a paused Routine approval across a full process restart. Hot reload preserves a resumable approval; a full restart system-cancels it as `producer_lost` and honestly settles the Run as `FAILED + outcomeUnknown`, so the user must run the Routine again. Future cross-restart resumption must persist and validate the complete continuation rather than retaining only the approval card.
- Windows installers remain unsigned until an Authenticode certificate is available, so Microsoft Defender SmartScreen may still warn on first download or launch.
